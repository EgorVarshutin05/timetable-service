# WP-03: создание, валидация и конфликты занятий

## Why

FR-01 и FR-02 требуют одинаковых BR-01..BR-07 при создании и предварительной
проверке, точного контракта и защиты от конкурентного нарушения BR-05.

## What Changes

- Добавляются чистые снимки данных и функции BR-01/02/04/05/06/07 в domain/.
- Группа проверяется до people-client; BR-01/02 выполняются до любых внешних I/O.
- Добавляются транзакционные advisory locks по отсортированным ключам ресурсов.
- Реализуются POST /lessons и POST /lessons/validate с общими правилами.
- Время нормализуется в UTC, нагрузка разбивается по локальным датам преподавателя.
- Добавляются изолированные domain/API-тесты, PostgreSQL-тесты и гонки.

## Capabilities

### New Capabilities

- `lesson-scheduling`: правила, создание и предварительная проверка расписания.

### Modified Capabilities

Нет: существующие GET, seed/reset и клиент предыдущих пакетов сохраняются.

## Impact

Новые domain/scheduling.py, repositories/scheduling.py, services/lessons.py.
Расширяются api/schemas.py, api/dependencies.py и api/lessons.py. В db.py явно
фиксируется READ COMMITTED; errors.py дополнен классификацией uuid_parsing как
400 BAD_REQUEST. Обновляется README. Нормативные YAML, зависимости и миграции
не меняются; ограничения БД уже созданы в WP-01.

## Trade-offs and Alternatives

- Advisory locks вместо SELECT FOR UPDATE по найденным занятиям: при пустом
  расписании нет строк для блокировки, а ресурс всё равно требуется защитить.
- Общая блокировка ресурса вместо ключа по дате проще, защищает интервалы через
  полночь и делает согласованным BR-06. Цена — сериализация непересекающихся
  операций с одним преподавателем/аудиторией/группой.
- Ключи BLAKE2b стабильны между процессами, в отличие от Python hash(). Коллизия
  может только добавить лишнее ожидание. Все ключи берутся в общем числовом порядке.
- Внешний HTTP выполняется между короткой проверкой группы и транзакцией записи:
  сетевое ожидание не держит соединение/locks; группа повторно читается под FOR SHARE.
- Предварительная проверка использует те же locks, но не резервирует слот. Её успех
  не гарантирует успех последующего создания при изменении расписания.
