# Зачем

FR-06..FR-10 требуют жизненного цикла после создания занятия: подтверждения,
отмены, завершения по BR-08, атомарного переноса и запуска по Clock.

# Что меняется

- Чистая статусная машина: confirm, cancel, reschedule, sweeper, complete.
- Четыре POST-операции по openapi.yaml, включая наследование полей переноса.
- Одна транзакция для RESCHEDULED + нового PLANNED; ровно один потомок.
- lesson-status-sweeper зарегистрирован в существующем JobRegistry.
- Явные границы успешного commit для публикации событий в WP-06 (FR-13).

# Trade-offs и альтернативы

Блокируем строку для статусных команд; перенос сначала берёт sorted union
ресурсных locks, затем строку. Optimistic UPDATE без повторной проверки статуса
и row-lock до advisory locks отвергнуты: нужны понятный 409 и общий порядок.
Во время HTTP транзакцию записи не держим; изменившийся PATCH-снимок перечитываем
с повторным HTTP. Это увеличивает вызовы при конкуренции, но сохраняет новые поля.
Sweeper использует FOR UPDATE без SKIP LOCKED: один запуск обрабатывает весь
подходящий набор, ожидая конкурента. Цена — ожидание занятых строк.
Публикация/брокер/outbox не реализуются этим пакетом; FR-13 — WP-06.
