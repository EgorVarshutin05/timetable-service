# Соглашения о работе в репозитории

Документ описывает, как ведётся работа над заданием: пакеты работ, ветки, коммиты, слияние в `master`, журнал времени и сдача. Соглашения одинаковы для всех заданий пула и проверяются автоматически — рецептом `just lint-commits`, в CI и при проверке работы. Результат проверки истории — материал для оценки процесса (критерий K7 в TASK.md §7); gate он не блокирует.

## 0. Коротко

1. `just setup` — один раз после клонирования: шаблон сообщения коммита и хук проверки.
2. Пакет работ WP-NN из Приложения C TASK.md → ветка `change/wpNN-<slug>` от `master` → OpenSpec change `openspec/changes/wpNN-<slug>/`.
3. Коммиты по Conventional Commits; `just check` зелёный перед слиянием.
4. `just merge-change wpNN-<slug>` — слияние в `master` merge-коммитом (`--no-ff`) с описанием пакета и footers `Change:` и `Refs:`.
5. README, раздел «Время» — собственная оценка до начала пакета и фактическое время после.
6. `git push --all && git push --tags`; тег `submission` — на последнем коммите `master`.

## 1. Пакеты работ и ветки

- Единица работы — пакет WP-NN (Приложение C TASK.md: состав FR и ориентировочная оценка). Один пакет — один OpenSpec change — одна ветка — одна строка в README «Время». У всех четырёх один идентификатор: `wpNN-<slug>`, где `<slug>` — 2–4 слова в kebab-case, начиная с глагола: `wp03-detect-lesson-conflicts`.
- Начало пакета: `git switch -c change/wp03-detect-lesson-conflicts master`, затем создание change (`proposal`, `specs`, при необходимости `design`, `tasks`). Первый коммит пакета обычно `spec(...)`.
- Ветка живёт от создания до слияния. Обновление ветки относительно `master` — `git rebase master` (предпочтительно) или `git merge master`. Перезапись собственной ветки до слияния допустима; `master` не перезаписывается никогда (без force-push и без rebase `master`).
- Несколько пакетов параллельно — допустимо, по одной ветке на пакет.
- Пакет, который не удалось завершить, в `master` не сливается: ветка остаётся в репозитории и пушится, пакет указывается в README «Не сделано» с именем ветки и причиной.

## 2. Коммиты: Conventional Commits

Формат заголовка: `<type>(<scope>)!: <description>`; scope и `!` необязательны.

| type | Когда используется |
| --- | --- |
| `feat` | новое поведение, наблюдаемое через API, события или фоновые задачи |
| `fix` | исправление ошибки в уже закоммиченном поведении |
| `refactor` | изменение структуры кода без изменения поведения |
| `perf` | производительность, в том числе async-кейс и его замер |
| `test` | только тесты и фикстуры |
| `docs` | README, docstring'и, комментарии |
| `spec` | OpenSpec-артефакты: proposal, specs, design, tasks, archive |
| `build` | зависимости, `pyproject.toml`, `uv.lock`, Dockerfile, compose |
| `ci` | конфигурация CI |
| `chore` | служебные изменения, не затрагивающие код приложения и тесты |
| `revert` | откат коммита (`git revert`); стандартный заголовок `Revert "…"` допустим |

Рекомендованные scope: `api` (HTTP-слой), `domain` (предметные правила), `db` (модели, миграции), `broker` (события, publisher/consumer, inbox, DLQ), `client` (клиент соседнего сервиса), `jobs` (фоновые задачи, `Clock`), `infra` (compose, Dockerfile, настройки, health), `e2e` (e2e-тесты и хелперы), `readme` и `openspec` (для `docs`/`spec`/`chore`). Другие scope допустимы, но отмечаются предупреждением.

Правила:

- Заголовок — на английском, в повелительном наклонении (`add`, не `added`), не длиннее 72 символов, без точки в конце.
- `!` после type/scope ставится, когда коммит меняет контракт: `openapi.yaml`, `asyncapi.yaml`, схему данных несовместимым образом. Контракт в задании нормативен, поэтому каждый `!` — отклонение, которое объясняется в README «Решения».
- Тело коммита отвечает на вопросы «что» и «почему», не «как». Отделяется от заголовка пустой строкой.
- Footers — в формате git trailers (`Token: value`), последним абзацем, через пустую строку. В содержательных коммитах желателен `Refs: FR-03, FR-07` (допустимы и NFR).
- В `master` не попадают временные коммиты: `fixup!`, `squash!`, `wip`. Перед слиянием они схлопываются: `git rebase -i --autosquash master`.
- Трейлеры AI-инструментов (`Co-Authored-By: …` и подобные) удалять не требуется.

Примеры:

```text
spec(domain): propose lesson conflict detection

Refs: FR-01, FR-02
```

```text
feat(domain): reject overlapping lessons in the same room

Conflicts are detected in the domain layer so that POST /lessons and
PATCH /lessons/{lesson_id} share one rule; the exclusion constraint in
the database is the last line of defence.

Refs: FR-01
```

```text
test(domain): cover touching intervals and cancelled lessons
```

## 3. Слияние пакета в `master`

Пакет готов к слиянию, когда его `tasks` закрыты (или оставшиеся перенесены в README «Не сделано»), OpenSpec change актуален (archive — до слияния или до сдачи) и `just check` зелёный на результате слияния.

Рецепт `just merge-change wp03-detect-lesson-conflicts`:

1. проверяет имя пакета и наличие ветки `change/<id>`, требует чистое рабочее дерево;
2. переключается на `master` и выполняет `git merge --no-ff --no-commit change/<id>`;
3. запускает `just check` на результате слияния; при ошибке слияние отменяется;
4. открывает редактор с шаблоном сообщения, в котором `Change:` и `Refs:` уже заполнены по текстам change.

Вручную то же самое: `git switch master && git merge --no-ff --no-commit change/<id> && just check && git commit`.

Формат merge-коммита: заголовок по Conventional Commits (type — по содержанию пакета, обычно `feat`), тело — описание изменения, как в merge request: что сделано, ключевые решения, как проверить; footers `Change:` и `Refs:` обязательны.

```text
feat(domain): detect lesson conflicts on create and move

Что изменилось: проверка пересечений занятий по аудитории и преподавателю
вынесена в domain-слой; POST и PATCH используют одно правило.
Решение: при конфликте — 409 SCHEDULE_CONFLICT с перечнем конфликтующих
занятий в details.
Как проверить: just test; just e2e-public (E2E-01, E2E-02).

Change: wp03-detect-lesson-conflicts
Refs: FR-01, FR-02
```

После слияния:

- ветка не удаляется и пушится вместе с `master`: `git push --all`;
- squash и fast-forward не используются — история пакета должна быть видна в `master`;
- merge request или pull request на хостинге не требуется: описание пакета живёт в merge-коммите, проверка читает только git.

Прямые коммиты в `master` допустимы только типов `docs` и `chore`, затрагивающие `README.md` и `openspec/` (итоговый журнал времени, archive). Код приложения, тесты и конфигурация попадают в `master` только через пакеты.

## 4. Журнал времени

Оценки в Приложении C ориентировочны: они задают объём, а не норматив скорости. Скорость выполнения не оценивается; отклонение факта от оценки на оценку работы не влияет. Журнал нужен для самопроверки понимания задачи, для калибровки задания и как материал дебрифа. Его правдоподобие сверяется с историей коммитов в грубом приближении.

Раздел README «Время» ведётся таблицей с фиксированными столбцами:

```markdown
## Время
| Пакет | Оценка задания, ч | Моя оценка до старта, ч | Факт, ч | Куда ушло время (при факте ≥ 2× оценки и ≥ +1 ч) |
| --- | --- | --- | --- | --- |
| wp01-… | 1,0 | 1,5 | 1,2 | — |
| Итого | 8,0 | | | |
```

- «Моя оценка до старта» заполняется до начала работы над пакетом. Расхождение с оценкой задания в 2 раза и более — повод перечитать FR пакета и либо задать вопрос через канал вопросов (TASK.md §9), либо зафиксировать принятую трактовку в README «Решения».
- «Факт» — чистое время в часах с точностью до 0,25 ч.
- Комментарий обязателен, если факт превышает оценку в 2 раза и более и не менее чем на 1 час; достаточно категории: трактовка требования, инфраструктура, отладка, тесты, работа с AI-ассистентом.

## 5. Автоматические проверки

`just lint-commits` проверяет историю от тега `scaffold-base` до `HEAD`; те же проверки выполняет CI и проверка работы (по тегу `submission`).

Нарушения (FAIL):

- заголовок не по Conventional Commits или с неизвестным type;
- `fixup!`, `squash!`, `wip` в истории `master`;
- merge-коммит пакета без footer `Change:`, `Refs:` или без описания; `Change:` не вида `wpNN-<slug>` или без соответствующего каталога в `openspec/changes/` (включая archive); `Refs:` с идентификаторами FR/NFR, которых нет в TASK.md;
- второй родитель merge-коммита не принадлежит ветке `change/<id>`;
- прямой коммит в `master` с изменениями вне `README.md` и `openspec/`.

Предупреждения (WARN): заголовок длиннее 72 символов, точка в конце, кириллица в заголовке, scope вне рекомендованного списка, прямой коммит в `master` не типа `docs`/`chore`, ветка `change/<id>` не найдена (удалена или не запушена), имя ветки не по соглашению.

Факты без оценки (INFO): число пакетов и коммитов, распределение типов, незавершённые ветки `change/*`, обратные слияния `master` в ветки.

`just setup` настраивает локальный репозиторий: `commit.template` на `.gitmessage` и `core.hooksPath` на `.githooks`, где хук `commit-msg` выполняет ту же проверку для каждого нового сообщения (для merge-коммита — с проверкой footers).

## 6. Сдача

1. Все завершённые пакеты слиты в `master`; незавершённые — в README «Не сделано».
2. README заполнен по шаблону Приложения A TASK.md, включая «Время» и «AI notes».
3. `just check` и `just lint-commits` на `master` — без FAIL.
4. `git tag -a submission -m "submission"` на последнем коммите `master`; `git push --all && git push --tags`.
5. Ссылка на репозиторий и имя тега отправляются по инструкции TASK.md §6.
