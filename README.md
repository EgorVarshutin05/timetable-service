## Решения

WP-01 (FR-04, FR-11, NFR-02, NFR-03). Разделил HTTP, запросы к БД и оркестрацию.
Предметные перечисления не зависят от FastAPI и SQLAlchemy. Группы и занятия хранятся
локально, преподаватели и аудитории — в people-stub, поэтому для них нет локальных FK.

Выбрал PostgreSQL INSERT ON CONFLICT (id) DO NOTHING: повторный seed сохраняет
существующие изменения и добавляет отсутствующие записи. UPSERT с обновлением
перезаписывал бы пользовательские данные. Полное восстановление выполняет только
POST /__test/reset: TRUNCATE lessons/groups и seed фиксируются одной транзакцией.
При ошибке откатывается и очистка. Clock в reset не передаётся и не меняется.

Для формата и статуса использую VARCHAR с CHECK вместо native enum — миграцию проще
откатывать. БД защищает длительность 30 минут–8 часов, порядок времени, сочетание
формата с аудиторией, ссылки на группу и источник переноса. UNIQUE на
rescheduled_from_id допускает несколько NULL и не больше одного потомка у источника.
Индексы под BR-05 помогают искать пересечения, но не заменяют блокировки WP-03.

Seed при старте выполняет lifespan; дублирующий запуск из Docker entrypoint убран.
Даты seed фиксированы; у ORM нет системных defaults времени. Ответы используют
существующий to_iso_z. Неверный UUID в GET даёт 400 BAD_REQUEST по общему соглашению
о формате и уточнению требований; отсутствующий ресурс — 404 NOT_FOUND. В YAML у
самих GET перечислены только 200/404; нормативный файл оставлен без изменений.

Исходную пустую миграцию 0001 заполнил по условию WP-01. Это допустимо для старта
задания; уже применённую рабочую миграцию в развёрнутом сервисе следовало бы расширять
новой ревизией. E2E-01 целиком проверяется после появления POST /lessons в WP-03.


WP-02 (FR-12, NFR-07, BR-03). Для people-stub использую один httpx.AsyncClient
на lifespan с адресом STUB_BASE_URL и таймаутом STUB_TIMEOUT_MS / 1000. HTTPX
добавлен в runtime-зависимости: dev/e2e-группы не устанавливаются в Docker-образ.
В domain возвращаю неизменяемые dataclass, UUID, Decimal и локальные time;
Pydantic-проверка внешнего ответа остаётся в clients/, без зависимости domain от HTTP.

Профиль, окна и аудитория запрашиваются через asyncio.gather; для ONLINE запросов
два, аудитория не запрашивается. gather(return_exceptions=True) дожидается всех
ответов и выбирает ошибку в порядке профиль → окна → аудитория, независимо от скорости.
Это исключает незавершённые фоновые запросы после ApiError, но быстрый отказ иногда
ожидает соседний вызов до его таймаута. Отмена вызывающей задачи отменяет дочерние
запросы и не превращается в 502/504. Скрытых повторов и кэша пока нет.

404 профиля/окон даёт 422 INSTRUCTOR_NOT_FOUND, 404 аудитории —
422 CLASSROOM_NOT_FOUND. TimeoutException обрабатывается раньше RequestError:
504 UPSTREAM_TIMEOUT против 502 UPSTREAM_UNAVAILABLE. Невалидный ответ 200,
неожиданный статус или несовпавший UUID также считаю отказом upstream (502).
I6 не считается доступным только потому, что его профиль ответил 200: ошибка окон
должна отклонить операцию. Комбинация format/classroom проверяется в BR-02 до
вызова адаптера; клиент не дублирует предметные HTTP-ошибки этого правила.

Ресурсы закрывает AsyncExitStack: сначала HTTP-клиент, затем engine, в том числе
при ошибке startup/seed. Readiness по-прежнему проверяет только БД и брокер.
trust_env=False исключает случайный HTTP_PROXY/ALL_PROXY для внутреннего stub;
конфигурацию адреса берёт только из настроек сервиса. SEED_ON_START, reset_state,
Clock и оба GET-эндпоинта WP-01 сохранены.


WP-03 (FR-01, FR-02). Вынес BR-01/02/04..07 в чистые функции domain/scheduling.py.
Роутеры отвечают за форму данных, service — за порядок I/O и транзакцию,
repository — за SQL. BR-01 и BR-02 выполняются до БД и HTTP. Группу сначала
проверяю короткой сессией, затем вызываю people-client; во время HTTP соединение
с БД освобождено. В транзакции повторно читаю группу под FOR SHARE, чтобы защитить
её размер и существование до записи.

Защита BR-05 — pg_advisory_xact_lock по преподавателю, группе и непустой аудитории.
Ключи BLAKE2b-64 стабильны между процессами и берутся в одном числовом порядке.
Блокировать только найденные строки через FOR UPDATE недостаточно: при пустом
расписании строк нет. Выбрал общую блокировку ресурса вместо дробления по датам:
так проще защитить перенос через полночь и дневную нагрузку; цена — меньший
параллелизм непересекающихся операций с одним ресурсом. Будущие команды изменения
должны использовать тот же протокол и объединение старых/новых ресурсов.

Изоляция явно READ COMMITTED. Запрос кандидатов идёт после захвата locks отдельным
statement и видит commit предыдущего владельца. В REPEATABLE READ снимок мог бы
остаться старым. Advisory locks освобождаются commit/rollback; они кооперативны
и не защищают от произвольного внешнего SQL, который игнорирует этот протокол.
Конфликты собираются целиком: instructor → classroom → group, внутри UUID
лексикографически. Касание границ не считается пересечением; COMPLETED учитывается,
CANCELLED/RESCHEDULED — нет. exclude_lesson_id исключается и из конфликтов, и из нагрузки.

Для BR-06 разрезаю интервалы по локальным полуночам преподавателя, а длительность
считаю в UTC через Decimal: при DST сутки могут длиться 23/25 часов. Окончание
ровно в полночь не добавляет нулевой следующий день. Предупреждения нагрузки идут
по датам, затем INSTRUCTOR_UNAVAILABLE. BR-07 требует одного полного окна;
соседние окна не объединяются. Для неоднозначной границы окна выбрано первое
вхождение (fold=0); окно с несуществующей DST-границей в этот день не используется.

POST /lessons останавливается на первом hard-нарушении: BR-04 раньше BR-05.
POST /lessons/validate возвращает обе 409-проблемы в violations при статусе 200,
сохраняя code/message/details; 400/422/502/504 не превращаются в violations.
Предварительная проверка не вставляет записи и не резервирует место. Новый урок —
PLANNED с UUID v4 и одинаковыми created_at/updated_at из одного Clock.now().
Ответ формируется после commit; все даты сериализуются существующим to_iso_z.
Числовые timestamps не принимаются, отсутствие offset даёт 422 fields;
неверный тип и UUID-формат — 400 BAD_REQUEST через общий errors.py.


WP-04 (FR-03, FR-05). Список объединяет фильтры по И, отбирает по
from <= starts_at < to и сортирует starts_at ASC, id ASC. limit=50 по умолчанию,
диапазон 1..200; offset=0 и неотрицателен. total считается до пагинации, в том
числе при пустой странице. Отсутствие status не исключает CANCELLED/RESCHEDULED.
Смещение в датах from/to обязательно по общему правилу задания. Случай from>=to
отдельно не описан; выбрал 422 VALIDATION_ERROR с details.fields.to. Все неверные
query-значения дают 422, как в контракте операции списка. Неизвестный валидный
UUID фильтра просто возвращает пустую страницу.

Count и items читаются в одной сессии REPEATABLE READ, чтобы не получить total
из одного состояния, а items — из другого при параллельной вставке. Сессия только
читает данные; SQLAlchemy сбрасывает переопределённую изоляцию при возврате соединения.
Транзакции записи сохраняют READ COMMITTED из WP-03 — после ожидания lock им нужен
новый снимок. Один уровень изоляции для этих двух задач был бы неверным компромиссом.

PATCH различает отсутствие поля и явный null через model_fields_set/exclude_unset;
exclude_none здесь не подходит. Только classroom_id допускает null. group_id,
status и created_at не редактируются. Форма JSON проверяется сразу, а значения
ISO/UUID/enum и BR — после проверки существования и PLANNED. Поэтому закрытое
занятие с неверным интервалом получает 409 LESSON_NOT_EDITABLE с current_status,
не обращаясь к people-stub. Сервис получает типизированную функцию применения
изменений, без импорта API-модели в services.

В write-транзакции беру sorted union advisory locks для старых и новых ресурсов,
затем SELECT FOR UPDATE и повторную проверку статуса. После этого читаю группу
FOR SHARE и вызываю прежний assess с exclude_lesson_id и collect_all=False.
При успехе меняются только разрешённые поля и updated_at из Clock; ошибка
откатывает все изменения. Само занятие исключено из конфликтов и дневной нагрузки.

Если между первоначальным чтением и FOR UPDATE другой PATCH изменил DraftLesson,
освобождаю транзакцию и повторяю объединение со свежим состоянием и HTTP-проверкой.
Сравнивать только updated_at нельзя: при замороженном Clock он одинаков у разных
обновлений. Добавлять новые locks после row-lock тоже нельзя — нарушился бы общий
порядок. Цена безопасного повтора — дополнительные HTTP-вызовы при конкуренции;
это не скрытый retry upstream-ошибок. При непрерывных изменениях возможны новые
циклы, операция остаётся отменяемой. Новые миграции и зависимости не понадобились.

## Async-кейс

Запросы к people-stub независимы: профиль преподавателя, недельные окна,
а для IN_PERSON ещё аудитория. При задержке каждого вызова 300 мс ожидаем около
900 мс последовательно и 300 мс параллельно; для ONLINE — 600 и 300 мс.

Воспроизведение без сети, БД, брокера и запущенной заглушки:

```bash
uv run pytest tests/unit/test_people_client.py -k test_async_case -q -s
```

Тест использует CountingTransport с asyncio.sleep(0.3), затем выполняет те же
вызовы последовательно и через get_lesson_people. Счётчик охватывает весь запрос;
в дополнение к времени проверяется max_in_flight == 3/2. Временной assert
относительный, с запасом для CI. Фактический замер при подготовке WP-02:

| Формат | Последовательно, мс | Параллельно, мс | Ускорение | max_in_flight |
| --- | ---: | ---: | ---: | ---: |
| IN_PERSON | 904,49 | 302,19 | 2,99× | 3 |
| ONLINE | 602,27 | 302,09 | 1,99× | 2 |

Числа зависят от машины и планировщика; это замер фейкового транспорта, а не
нагрузочный тест работающего сервиса. Он подтверждает NFR-07. Дополнительно тест
`test_original_stub_stats_over_asgi` запускает исходный stub без изменений через
ASGITransport и проверяет его настоящий GET /__stub/stats (два подчёркивания),
total, max_in_flight, in_flight=0 и сброс счётчиков. Служебные запросы не учитываются.

```bash
uv run pytest tests/unit/test_people_client.py -k original_stub_stats -q
```

Таймауты в custom transport моделируются явным httpx.ReadTimeout: HTTPX не
превращает задержку пользовательского транспорта в сетевой timeout. В рабочем
клиенте настроены connect/read/write/pool таймауты. Endpoint и сценарии реальной
заглушки не менялись; в WP-03 клиент подключён
к POST /lessons и POST /lessons/validate. Проверка реального max_in_flight
через внешний e2e остаётся частью итогового прогона стека.
